# 云文档套件发布到思源集市

本仓库已经列入思源集市。更新现有插件时，发布新的 GitHub Release 即可；不需要每次再向 Bazaar 提交 PR。仓库的 `.github/workflows/release.yml` 在推送 `v*` 标签后运行测试、构建，并把单个 `package.zip` 附到 Release。集市随后读取新的版本和安装包。

## 一次性准备

在本机安装 Node.js 24、pnpm 11、Git 和 GitHub CLI。先完成一次 GitHub CLI 登录并配置 Git 凭据：

```powershell
gh auth login -h github.com --web
gh auth setup-git
gh auth status
git ls-remote origin HEAD
```

如果 `gh auth status` 提示 token 无效，请重新登录；如果 `git ls-remote` 无法连接 GitHub，先修复本机网络或代理。密钥不得写入仓库、发布包或更新公告。发布脚本在认证和网络检查失败时会停止，不会退回网页逐文件上传。

## 每次发布

1. 在 `main` 上完成并提交代码，确保与 `origin/main` 一致。
2. 同时更新 `plugin.json`、`package.json` 的版本号；在 `RELEASE_NOTES_CURRENT.md` 写本次公告，并更新 `RELEASE_NOTES.md` 与 README 中的版本摘要。
3. 在仓库根目录执行一条命令：

```powershell
pwsh -File scripts/release.ps1 -Version 2.3.3
```

脚本会检查版本、公告、Git 状态和远端标签，运行自动测试、浏览器回归、类型检查与构建，校验 `package.zip` 后推送版本标签。GitHub Actions 自动生成 Release 和正式安装包；脚本等待 `package.zip` 可见。只想先验证本地包时使用 `-VerifyOnly`，不会推送标签：

```powershell
pwsh -File scripts/release.ps1 -Version 2.3.3 -VerifyOnly
```

若标签已推送而 Actions 失败，先查看仓库 Actions 日志并修复，不要重复创建同名标签。集市通常在 GitHub Release 出现后异步刷新；思源客户端可能需要稍后刷新或重启。

## 安装包内容

`scripts/build.mjs` 生成主程序，`scripts/package.mjs` 将主程序、脑图/表格/白板等编辑器页面、图标、清单和更新记录打成**一个** `package.zip`。仓库里的 `static/mm-editor.js` 等文件是插件源码，不是独立插件。只上传版本号和公告而不提交这些源码，会让 GitHub Actions 从旧代码构建安装包。
